# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직** (계산, 변환, 상태 전이, 검증)
- **API** (핸들러, 요청/응답 처리, 에러 매핑)
- **유틸 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트부터 작성)

### TDD 불필요

- **타입 정의** (`type`, `interface`)
- **설정 파일** (빌드, 린트, tsconfig 등)
- **순수 UI** (로직 없는 마크업, 스타일링)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면 **적용한다**. UI 안에 로직이 있으면 로직을 분리해 TDD로 작성한다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 마라.
- 테스트 이름은 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### 2. GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 마라.
- **신규 테스트 + 기존 테스트 전부** 실행해 통과를 확인한다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경 후마다 실행한다.
- **새 동작 추가 금지.** 새 동작은 다음 RED에서 한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 삭제 강제

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억에 의존한 재작성 모두 포함한다.
- 삭제 후에는 테스트부터 새로 쓴다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 자주 깨진다. 테스트는 30초면 쓴다. 단순하면 더 빨리 끝난다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓴 것이라 버그를 잡지 못한다. 그리고 나중은 오지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD가 더 빠른 길이다. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. 삭제하고 RED부터 시작한다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 삭제가 쉬우니 더더욱 TDD 예외가 아니다. |
